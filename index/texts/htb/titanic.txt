## Red Team Penetration Testing Report

### Overview
This report documents the security weaknesses identified during the assessment of `titanic.htb`. 
The engagement led to privilege escalation from an initial foothold to full domain compromise.

---

## Findings and Recommendations

### Finding 1: **Open Network Ports and Services**
#### Identified Ports:
```bash
PORT     STATE SERVICE        VERSION
22/tcp   open  ssh            OpenSSH 8.2p1 Ubuntu 4ubuntu0.12 (Ubuntu Linux; protocol 2.0)
80/tcp   open  http           Apache httpd 2.4.41 (Ubuntu)
```

#### Risk Rating:
- **Medium:** The web server is running Apache 2.4.41 on Ubuntu, which may have known vulnerabilities.
- **Medium:** The SSH service is publicly accessible, which increases the risk of brute-force or credential stuffing attacks.
- **Low:** Default SSH keys are exposed in the fingerprint output, potentially aiding fingerprint-based attacks.

#### Recommendations:
- Restrict SSH access to specific IP addresses using firewall rules.
- Enforce key-based authentication and disable password authentication.
- Regularly rotate SSH host keys and monitor for unauthorized access attempts.
- Upgrade Apache to the latest stable version to mitigate security vulnerabilities.
- Remove unnecessary files like README.md and web.config to reduce information leakage.
- Implement security headers to mitigate web-based attacks.

---

### Finding 2: **Local File Inclusion (LFI) in /download Endpoint**

#### Observation:
- The /book endpoint allows users to download a JSON file.
- After submitting the form, the request is redirected to /download?ticket=rand-id.json.
- By modifying the ticket parameter, it was possible to retrieve system files.
- Example: Replacing rand-id.json with ../../../../etc/passwd successfully returned the contents of /etc/passwd.

#### Risk Rating:
- **High:** LFI vulnerabilities can allow attackers to read sensitive files, leak credentials, and potentially escalate to Remote Code Execution (RCE).

#### Recommendations:
- Input Validation: Implement strict input validation and allow only expected filenames.
- Disable Directory Traversal: Use realpath() or restrict directory access with chroot/jail techniques.
- Sanitize User Input: Ensure user-controlled input is properly sanitized before being used in file operations.
- Least Privilege: Restrict file read permissions for the web application user.

---

### Finding 3: **Exposed Gitea Instance on dev.titanic.htb**

#### Observation:
- dev.titanic.htb hosts a Gitea instance requiring authentication.
- A new user can be registered, allowing access to repositories.
- Two repositories of interest were found:
- flask-app: Confirms the code flaw responsible for LFI but contains no additional credentials.
- docker-config: Reveals that Gitea runs inside a Docker container and stores data in /home/developer/gitea/data.

#### Risk Rating:
- **Medium:** Unauthorized access to internal repositories may expose sensitive application configurations and source code vulnerabilities.

#### Recommendations:
- Restrict Gitea registration to authorized users only.
- Implement access control to prevent repository enumeration by unauthorized users.
- Ensure secrets and sensitive files are not stored in public repositories.


---

### Finding 4: **Extraction of Gitea Database via LFI**
#### Observation:
- Gitea stores user data in an SQLite database located at /home/developer/gitea/data/gitea/gitea.db.
- Using the LFI vulnerability, an attacker can download the database file:

```bash
curl -s "http://titanic.htb/download?ticket=/home/developer/gitea/data/gitea/gitea.db" -o gitea.db
```
- Accessing the database with SQLite reveals user credentials:

```bash
sqlite3 gitea.db
sqlite> SELECT lower_name, passwd, salt FROM user;
```
- The extracted password hashes and salts can be cracked offline.

#### Risk Rating:
- **High:** Extraction of the Gitea database exposes sensitive user credentials, enabling offline password cracking and potential account takeover. 
This could lead to unauthorized access, privilege escalation, and further exploitation of the system.

#### Recommendations:
- **Restrict Access:** Ensure that the /download endpoint does not allow traversal to sensitive files outside its intended scope.
- **Encrypt Sensitive Data:** Store passwords using strong hashing algorithms (e.g., bcrypt, Argon2) with proper salting to slow down brute-force attempts.
- **Implement File Permissions:** Ensure that web applications do not have unnecessary read access to sensitive database files.
- **Regularly Rotate Credentials:** Force password resets for affected users and implement multi-factor authentication (MFA) where possible.

## Findings and Recommendations

### Finding 5: **Privilege Escalation via ImageMagick Exploit**

#### Observation:
- The /opt/scripts/identify_images.sh script calls ImageMagick’s identify command on uploaded images.
- ImageMagick version 7.1.1-35 is in use, which is vulnerable to an arbitrary code execution exploit.
- An attacker can craft a malicious .mvg or .svg file to execute arbitrary commands when processed by ImageMagick.
- Exploit Demonstration:
- A malicious shared library (.so) can be created to execute arbitrary commands:

```
#include <stdio.h>
#include <stdlib.h>
__attribute__((constructor)) void init(){
    system("Exploit Command");
    exit(0);
}
```
- When processed, the payload executes, enabling actions such as spawning a reverse shell.

#### Risk Rating:
- **Critical**: Exploiting this vulnerability allows an attacker to execute arbitrary code as the user running the script, 
potentially escalating privileges to root.

#### Recommendations:
- **Update ImageMagick**: Upgrade to the latest patched version to mitigate known exploits.
- **Use a Secure Execution Environment**: Run image processing scripts in a restricted, sandboxed environment with minimal privileges.
- **Sanitize Inputs**: Validate and restrict uploaded files to only allow safe image formats.
- **Apply the Principle of Least Privilege**: Ensure the script runs with the least privileges necessary to perform its function.

---

## Conclusion
The penetration test of titanic.htb uncovered multiple critical vulnerabilities that allow an attacker to gain unauthorized access, 
escalate privileges, and potentially take full control of the system.
Local File Inclusion (LFI) in /download Endpoint exposed sensitive files, enabling reconnaissance and data exfiltration.
Exposed Gitea Instance on dev.titanic.htb allowed unauthorized access to internal repositories, revealing application source code and configurations.
Extraction of Gitea Database via LFI provided access to user credentials, which could be cracked offline for unauthorized account takeover.
Privilege Escalation via ImageMagick Exploit allowed arbitrary code execution, ultimately leading to root access.
These findings highlight the need for immediate remediation to prevent exploitation. Addressing LFI, securing exposed services, 
restricting access to sensitive data, and updating vulnerable software are critical steps in mitigating these risks. 
Failure to do so could result in a full system compromise, data breaches, and unauthorized access by malicious actors.
